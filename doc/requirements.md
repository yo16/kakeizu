# 家系図サービス 要件定義書

- バージョン: 0.6 (ドラフト)
- 最終更新日: 2026-04-17
- 作成者: yo16

---

## 1. サービス概要

### 1.1 目的
個人・家族単位で、自分のルーツや家族構成を視覚的・構造的に記録し、写真やエピソードと共に後世に残せる Web サービスを提供する。

### 1.2 コンセプト
- **パーソナル**: 一般ユーザーが自分の家系・ルーツを気軽に整理できる
- **リッチ**: 氏名・続柄などの基本データだけでなく、写真・エピソード・経歴などの物語も記録できる
- **ビジュアル**: 縦型ツリーを軸に、ブラウザ上でインタラクティブに閲覧・編集できる
- **共有可能**: URL を知る家族と閲覧を共有できる（編集権限は作成者のみ）
- **フリーミアム**: 基本機能は無料で利用でき、登録人数・写真枚数の上限を有料プランで拡張できる

### 1.3 プロダクトの非目標 (Non-Goals)
- 家系研究・系図学のための専門ツールではない（GEDCOM などの業界標準互換は初期スコープ外）
- 大規模家系（数千人規模）のハイパフォーマンス運用は想定しない
- ソーシャルネットワーク的な他ユーザーとの交流機能は提供しない

---

## 2. ターゲットユーザー

| 区分 | 内容 |
|---|---|
| 主利用者 | 一般の個人ユーザー（自分の家系・家族を整理したい人） |
| 副利用者 | 作成者から URL を共有された家族（閲覧のみ） |
| 利用規模 | 1 家系あたり数十人程度の小規模を主ターゲット |
| 利用シーン | 自宅の PC・タブレット等での個人利用。家族の集まりで閲覧・共有など |

## 3. スコープ

### 3.1 MVP (初回リリース) に含める機能
- ユーザー認証（メール+パスワード / OAuth）
- ツリー（家系図）の作成・編集・削除
- 人物の登録・編集・削除（基本情報、続柄、婚姻、養子縁組、写真、エピソード、経歴）
- 複数の配偶者 / 再婚 / 養子・連れ子 / 子なし・未婚 / 同性パートナーなどの特殊ケース対応
- 縦型ツリーによるインタラクティブな表示（ズーム・パン）
- PDF / 画像としてのエクスポート
- URL リンクによる閲覧共有（閲覧者は編集不可）
- タイムライン表示（年表と家系図の連動）
- 人物に紐づく写真の複数登録 + 年表連動による顔写真の自動切替
- サブスクリプション課金（Stripe 連携。無料 / ベーシック / スタンダードの 3 プラン）

### 3.2 MVP では含めない機能（将来検討）
- GEDCOM などの外部フォーマットのインポート/エクスポート
- CSV/JSON 一括インポート
- 家族メンバーを招待しての共同編集
- 地図表示（居住地プロット）
- 検索・フィルタ機能（氏名・世代などでの絞り込み）
- 存命者の同意確認フラグ機能
- 横型ツリー表示
- モバイル専用 UI の最適化

## 4. 機能要件

### 4.1 ユーザー管理
- **FR-U1**: ユーザーはメールアドレス + パスワードでサインアップ・サインインできる
- **FR-U2**: ユーザーは Google OAuth でサインインできる（MVP では Google のみ。他プロバイダは将来検討）
- **FR-U3**: ユーザーは自分のアカウントを削除できる。削除時は所有するすべての家系図・人物・写真データも削除される
- **FR-U4**: 未認証ユーザーは共有 URL 経由のみ家系図を閲覧できる（読み取り専用）

### 4.2 家系図 (ツリー) 管理
- **FR-T1**: 認証ユーザーは複数の家系図を作成できる。作成可能数は契約中のプランの上限（FR-B2 参照）に従う
- **FR-T2**: 家系図にはタイトル・説明・作成者情報を設定できる
- **FR-T3**: 家系図ごとに共有 URL を発行・無効化できる
- **FR-T4**: 家系図を削除できる（削除時は関連する人物・写真も削除）

### 4.3 人物管理
- **FR-P1**: ユーザーは家系図に人物を追加・編集・削除できる。1 つの家系図に登録できる人数は契約中のプランの上限（FR-B3 参照）に従う
- **FR-P2**: 人物の登録項目
  - 必須: 氏名（または表示名）
  - 任意: 旧姓、性別、生年月日、没年月日、出生地、没地、エピソード / 経歴（自由記述のリッチテキストまたはプレーン長文）、顔写真、関連写真、存命フラグ
- **FR-P3**: 生没年月日は不明（年のみ、月のみ等）も許容する（曖昧な日付表現をサポート）
- **FR-P4**: 人物同士の関係を登録できる
  - 親子関係（実親 / 養親を区別可能）
  - 婚姻関係（配偶者、事実婚、同性パートナー、元配偶者を区別可能）
  - 1 人に対して複数の配偶者・複数の親を登録できる
- **FR-P5**: 関係の矛盾（自分が自分の祖先になるなど）は登録時にバリデーションで防ぐ

### 4.4 写真・メディア管理
- **FR-M1**: 人物に対して複数枚の写真を登録できる。1 人あたりに登録できる写真枚数は契約中のプランの上限（FR-B3 参照）に従う
- **FR-M2**: 各写真には撮影日（年のみ・年月のみ可）、キャプション、写っている人物の関連付け（1 枚に複数人物の紐付けが可能）を設定できる
- **FR-M3**: 代表写真（デフォルト顔写真）を 1 枚選択できる
- **FR-M4**: 写真は Supabase Storage に保存し、サムネイルを自動生成する（方針は設計フェーズで確定）
- **FR-M5**: アップロード可能な形式は JPEG / PNG / WebP、1 枚あたりの上限サイズは設計フェーズで定める
- **FR-M6**: アップロード時にクライアント側で画像を圧縮・リサイズしてからサーバーに送信する。egress コストと表示パフォーマンスを抑えるため、原寸保持は行わない（推奨値の目安: 長辺 2048px、JPEG 品質 85%。具体値は設計フェーズで確定）
- **FR-M7**: Supabase Storage の Image Transformation API を用いて、表示用途に応じたサイズ（サムネイル / 詳細パネル / フルビュー）を配信する

### 4.5 ツリー表示 (ビジュアライゼーション)
- **FR-V1**: 縦型ツリー（上から下へ世代が進む）で家系図を表示する
- **FR-V2**: マウス / タッチによるズーム・パン操作ができる
- **FR-V3**: 人物ノードをクリック / タップすると詳細パネル（写真・基本情報・エピソード・関連写真）が表示される
- **FR-V4**: 特殊ケース（複数配偶者、養子関係、連れ子など）が視覚的に区別できる（線種・色などで表現）
- **FR-V5**: 人物ノードにホバー / タップすると近接ボタン（「+親」「+子」「+配偶者」）が表示され、そこから新規人物を追加できる。追加後はフォームで詳細項目を入力する
- **FR-V6**: 初回起動時に、自分自身を起点として家系を登録するウィザード形式のオンボーディングを提供する（例: 「あなた → 両親 → 兄弟姉妹 → 配偶者 → 子」の順に質問して登録）。ウィザードはいつでもスキップ・中断可能とする
- **FR-V7**: 既存人物同士を選択して関係（婚姻・親子など）を後付けで設定できる。新規追加フローとは別に「既存人物と関係付け」の導線を用意する

### 4.6 タイムライン連動
- **FR-TL1**: 家系図と並行して、登録人物のイベント（生誕・婚姻・没）を横断的に年表表示する
- **FR-TL2**: 年表上で時点 (年) を選択すると、人物詳細パネルの顔写真を、その時点に最も近い撮影日の登録写真に自動切替する
- **FR-TL3**: 撮影日のない写真はタイムライン連動の対象外（代表写真にフォールバック）

### 4.7 エクスポート
- **FR-E1**: 家系図を PDF としてエクスポートできる
- **FR-E2**: 家系図を画像 (PNG) としてエクスポートできる
- **FR-E3**: エクスポート時のサイズ・用紙方向はユーザーが選択できる（詳細は設計フェーズ）

### 4.8 共有
- **FR-S1**: 作成者は家系図ごとに共有 URL を生成できる
- **FR-S2**: 共有 URL を持つユーザー（未ログインを含む）は家系図を閲覧のみできる（編集・エクスポート不可）
- **FR-S3**: 作成者はいつでも共有 URL を無効化（再発行）できる

### 4.9 課金・サブスクリプション
- **FR-B1**: Stripe を利用してサブスクリプション課金を行う
- **FR-B2**: ユーザーは以下の 3 プランから選択できる（通貨は JPY、料金は内税表示・固定価格。MVP では Stripe Tax は使用しない）

| プラン | 月額料金 (内税) | 作成可能な家系図数 | 1 家系図あたりの人物登録上限 | 1 人あたりの写真登録上限 |
|---|---|---|---|---|
| Free（無料） | ¥0 | 1 個 | 5 人 | 2 枚 |
| Basic（ベーシック） | ¥500 / 月 | 2 個 | 20 人 | 5 枚 |
| Standard（スタンダード） | ¥2,000 / 月 | 5 個 | 40 人 | 10 枚 |
| Enterprise（要相談） | 個別見積り | 無制限 | 40 人超 | 10 枚超 |

- **FR-B3**: 人物の追加・写真のアップロード時にプランの上限を超える場合、サーバー側でリクエストを拒否し、ユーザーに上限到達とアップグレード導線を提示する
- **FR-B4**: 未認証ユーザーおよび新規登録直後のユーザーは Free プランが自動的に適用される
- **FR-B5**: ユーザーは Stripe Checkout を経由して有料プランへアップグレードできる
- **FR-B6**: ユーザーは Stripe Customer Portal（または同等の自前画面）を通じて、プラン変更・解約・支払い方法の更新・請求履歴の確認ができる
- **FR-B7**: 契約状態は Stripe Webhook を受信してアプリ側の DB に反映する（`checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed` 等）
- **FR-B8**: 支払い失敗時は、Stripe のリトライ期間中は現プランを維持し、リトライ終了後に Free プランへ降格する（具体的な猶予期間は設計フェーズで確定）
- **FR-B9**: 解約時は当該課金期間終了までは現プランを維持し、期間終了後に Free プランへ降格する
- **FR-B10**: プラン降格時に上限超過データが存在する場合の挙動
  - 既存データは削除しない（閲覧・エクスポートは引き続き可能）
  - 新規追加・新規アップロードは上限内に収まるまで不可とする
  - ユーザーに超過状態であることを明示する UI を提示する
- **FR-B11**: Enterprise プランは MVP 時点では「お問い合わせ窓口への誘導」のみ実装し、自動プロビジョニングは行わない
- **FR-B12**: 課金関連の操作（Checkout, Webhook）はすべてサーバーサイドで処理し、クライアント側にシークレットキーを露出しない

## 5. 非機能要件

### 5.1 パフォーマンス
- **NFR-P1**: 数十人規模の家系図を 3 秒以内に初期表示する（通常のブロードバンド環境）
- **NFR-P2**: ノード追加・編集などの操作レスポンスは 1 秒以内を目標とする

### 5.2 ユーザビリティ
- **NFR-U1**: PC ブラウザ（Chrome / Safari / Edge 最新版）をメインに、タブレットでも操作可能なレスポンシブデザインとする
- **NFR-U2**: 人物の追加・関係の設定が直感的に行える UI を提供する

### 5.3 セキュリティ
- **NFR-S1**: ユーザーデータは Supabase の RLS (Row Level Security) で他ユーザーから隔離する
- **NFR-S2**: 共有 URL はランダムなトークン（推測困難）で構成する
- **NFR-S3**: パスワード認証は Supabase Auth の標準（ハッシュ化・メール検証）に準拠する
- **NFR-S4**: 個人情報保護に関する特別な要件は MVP では設けず、利用規約で運用上の注意を明示する
- **NFR-S5**: クレジットカード情報はアプリ側で一切保持せず、すべて Stripe に委ねる（PCI DSS の直接対応範囲を最小化）
- **NFR-S6**: Stripe Webhook は署名検証を必須とし、不正リクエストを拒否する

### 5.4 可用性・運用
- **NFR-A1**: 稼働率目標は Supabase / ホスティング先の SLA に準拠する（個別の高可用性要件は設けない）
- **NFR-A2**: データの定期バックアップは Supabase の標準機能に委ねる
- **NFR-A3**: Supabase Free プランは一定期間アクセスがないとプロジェクトが自動停止（pause）される仕様であるため、定期的に DB へ書き込みを行う「キープアライブ」処理を運用する。GitHub Actions のスケジュール起動で 2 日に 1 回程度、専用テーブルへ現在日時を INSERT する。Pro プラン移行後は不要となるため、運用切替を行えるよう設計する

### 5.5 スタイリング / デザイン
- **NFR-D1**: スタイリングは CSS Modules + CSS Custom Properties で実装する（Tailwind CSS は使用しない）
- **NFR-D2**: デザイントーンは柔らかく、家族向けサービスにふさわしい温かみのあるビジュアルを採用する

## 7. データモデル（概念レベル）

詳細は設計フェーズで確定するが、主要エンティティは以下:

- **User** — 認証アカウント
- **Tree** — 家系図。User が所有。ShareToken を持つ
- **Person** — 人物。Tree に属する
- **Relation** — 人物間の関係（親子 / 婚姻）。タイプ（実親・養親・配偶者・元配偶者 等）を持つ
- **Photo** — 写真。Tree に属し、複数の Person と多対多で関連付けられる。撮影日・キャプションを持つ
- **ShareLink** — 共有 URL のトークン、有効/無効フラグ
- **Plan** — プランのマスタ（Free / Basic / Standard / Enterprise、料金、人物上限、写真上限、Stripe Price ID）
- **Subscription** — User と Plan の現在の契約状態（Stripe Customer ID, Stripe Subscription ID, ステータス, 次回課金日, 期間終了日）
- **BillingEvent** — Stripe Webhook の受信ログ（冪等性確保・監査用）

## 8. 既知のリスク・オープン事項

| ID | 内容 | 対応方針 |
|---|---|---|
| R-1 | 複雑な家系構造（再婚・養子など）のレイアウトアルゴリズム | 設計フェーズで既存 OSS (dagre, d3-hierarchy など) の適用可能性を調査 |
| R-2 | PDF / 画像エクスポート時の大規模ツリーの描画 | 初期はクライアントレンダリング + html-to-image 等を想定。サーバーサイド描画は将来検討 |
| R-3 | 存命者の個人情報を家族以外の第三者が閲覧するリスク | MVP は共有 URL の厳格なトークン管理 + 利用規約で対応。将来的に同意確認フラグを追加検討 |
| R-4 | 写真ストレージのコスト | 1 ユーザーあたりのアップロード上限を設ける（具体的な上限値は設計フェーズで確定） |
| O-1 | OAuth プロバイダのラインナップ | **確定**: MVP は Google + メール+PW のみ。他プロバイダは将来検討 |
| O-2 | 曖昧な日付表現のデータ型定義 | 設計フェーズで確定（例: year/month/day を個別カラム化） |
| O-3 | 家系図の作成数自体への上限設定（プランごと） | **確定**: Free=1, Basic=2, Standard=5, Enterprise=無制限（FR-B2 に反映済） |
| O-4 | 無料トライアル / 年額プランの提供有無 | MVP では月額のみ。将来検討 |
| O-5 | 消費税の扱い（内税 / 外税 / インボイス対応） | **確定**: 内税表示・固定価格。Stripe Tax は使用しない（インボイス対応は将来検討） |
| O-6 | Enterprise プランの申込・見積りフロー | MVP ではメールフォーム等の問い合わせ窓口のみ。本格的な運用は将来検討 |
| O-7 | 支払い失敗時のリトライ猶予期間 | Stripe の Smart Retries を基本とし、Free プラン降格タイミングの具体値は設計フェーズで確定 |
| O-8 | 返金ポリシー | 原則として日割り返金なし（Stripe の請求期間単位）。利用規約で明示 |
| O-9 | 画像配信基盤のスケール戦略 | MVP は Supabase Storage + Image Transformation API で十分。egress・ストレージ使用量を継続的にモニタリングし、閾値（例: 月次 egress 200GB 超、ストレージ 80GB 超）を超えた場合に Cloudflare R2 等への移行を検討する。具体的な閾値・移行先候補は設計フェーズで確定 |
